Trabajar con una herramienta como Antigravity CLI requiere una estrategia de **instrucciones atómicas y contextuales** para evitar alucinaciones, código a medio terminar o dependencias rotas entre el backend y el frontend.

### 1. Regla de oro: Una tarea técnica a la vez (Enfoque TDD/Iterativo)

Nunca le pegues una fase entera (ej: *"Haceme la Fase 2 completa"*). En su lugar, desglosá cada fase en **prompts de unidad ejecutable** que sigan el ciclo: **Estructura $\rightarrow$ Lógica de Negocio $\rightarrow$ Tests $\rightarrow$ Siguiente tarea**.

### 2. Estructura recomendada para armar tus Prompts

Cada vez que le pidas algo al CLI, usá esta plantilla mental de 4 partes:

1. **Contexto:** Dónde estamos parados y qué stack usamos.
2. **Objetivo único:** Qué archivo, endpoint o componente debe crear/modificar.
3. **Restricciones/Reglas:** Multi-tenancy obligatorio, tipos, validaciones o paquetes a usar.  
4. **Criterio de éxito (Test):** Cómo validamos que está terminado antes de pasar a la siguiente tarea.

### 3. Secuencia de comandos paso a paso sugerida

Seguí el orden de dependencias que definimos, enviándole tareas granulares como estas:

#### Bloque 1: Infraestructura y Setup Base (Fase 1)

1. **Tarea 1.1:** "Crea el archivo `docker-compose.yml` para desarrollo con 5 servicios: `backend` (PHP 8.3 FPM con extensiones pdo_pgsql y redis), `frontend` (Node 22 Alpine), `database` (PostgreSQL 16), `cache` (Redis Alpine) y `webserver` (Caddy). Configurá los volúmenes y redes internas."  
2. **Tarea 1.2:** "Dentro de la carpeta `/backend`, inicializá un proyecto Laravel 11 limpio configurado para conectarse a las variables del `docker-compose.yml`."  
3. **Tarea 1.3:** "Diseñá las migraciones de base de datos para multi-tenancy y feature flags: tablas `complejos`, `modulos`, `planes`, `plan_modulo` y `complejo_modulo`. Creá los seeders con los planes Bronce, Plata y Oro."  

#### Bloque 2: Core de Reservas y Concurrencia (Fase 2)

1. **Tarea 2.1:** "Creá las migraciones para `canchas` y `turnos` con su foreign key `complejo_id`. Implementá un `TenantScope` global en Eloquent para filtrar automáticamente por el complejo autenticado."  
2. **Tarea 2.2:** "Construí el servicio `DisponibilidadService` que calcule los slots libres de una cancha para una fecha dada cruzando los horarios del club con los turnos existentes."  
3. **Tarea 2.3:** "Implementá la lógica de bloqueo temporal atómico en Redis (`turno:cancha_id:fecha:hora` con TTL de 10 min) en el endpoint `POST /api/turnos/bloquear-temporal`. Escribí el test unitario que verifique que un segundo intento retorne 409 Conflict."  

#### Bloque 3: Middleware y CMS en Next.js (Fases 4 y 3)

1. **Tarea 3.1:** "En `/frontend`, creá el `middleware.ts` de Next.js para capturar el subdominio de la cabecera `Host` y reescribir la ruta hacia `/tenants/[subdomain]` de forma transparente."  
2. **Tarea 3.2:** "Creá la página pública `[subdomain]/paginas/[slug]` utilizando `getStaticProps` e ISR con revalidación on-demand."  

### 4. Consejos clave al interactuar con el CLI

- **Obligalo a verificar antes de avanzar:** Siempre cerrá el prompt pidiéndole: *"Escribí el test automatizado para este endpoint/componente y ejecutalo"*. No pases a la siguiente tarea hasta que el test pase en verde.  
- **Mantené el contexto limpio:** Si cambiás de módulo (por ejemplo, pasás del motor de reservas al CMS), recordale explícitamente el aislamiento: *"Recordá que este modelo debe incluir `TenantScope` y validar el middleware `tenant.has_module`"*.  
- **Commit por cada tarea:** Cada vez que el CLI termine una tarea funcionalmente completa y testeada, hacé un `git commit` en tu repositorio antes de pedirle la siguiente. Si el CLI rompe algo en la siguiente instrucción, podés volver atrás inmediatamente con `git rollback`.
